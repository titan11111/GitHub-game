# 251-sushi-kanji-shobu ｜ 寿司漢字勝負

## 一言

客はカタカナで注文し、職人は漢字の札で応える。**手を空けておくか、高い札を取りに行くか**を毎回選ぶ、カウンター越しの一本勝負。

## 基本情報

| 項目 | 内容 |
|---|---|
| ジャンル | 対戦クイズ（漢字 × リソース管理） |
| 構成 | 単一HTML（`index.html` のみ・外部依存ゼロ・画像/音声ファイルなし） |
| サイズ | 見込み 60KB以下（20MB鉄則の0.3%以下）※未実測 |
| 画面 | iPhone縦持ち基準。DOM主体（Canvasは使わない） |
| 音 | WebAudio の合成音のみ（ファイル不要・iOSはタッチで解錠） |
| 一席（1プレイ） | 90秒 ※未実測・要調整 |
| 対戦 | 左＝プレイヤー／右＝CPU の1対1 |

## 勝敗条件

**90秒で握った貫数が多い方が勝ち。** 同数は引き分け（延長なし）。

## コアループ

```
客がカタカナで1つ注文する（両職人に同時に見える）
  ↓
手が空いている方が、品書き16枚から漢字の札をタップ
  ↓
┌ 正解 → その注文を取る。難易度に応じた時間だけ握る（手が塞がる）
└ 誤答 → 2秒お手つき（手が止まる）＋ その注文は相手に進呈される
  ↓
握り終わると貫数が入り、手が空く。次の客が注文する
```

## 設計の芯：採用した3つの決定（2026-09-22 タイタン裁可）

### 1. 取り合い ＋ お手つきは「相手への進呈」

誤答の罰を「2秒失う」だけにしない。**間違えた瞬間、その注文は相手のものになる。**

- 相手の手が空いていれば、相手はそのまま握りに入る
- 相手が握り中なら、相手側に**予約札**として積まれ、握り終わり次第そのまま得点になる

これで毎回「早く押すか、確信してから押すか」の判断が発生する。取れなかった側も**相手のミス待ち**という能動的な時間になり、2人対戦の最大の弱点である「負けた側の空白」が埋まる。

### 2. 握り時間を戦術にする

**注文は常に1件ずつ。** だから握っている間に来た注文は、相手が無競争で取れる。

> 特上（2.2秒）を取る = 次の1〜2件を相手に渡す
> 並（0.8秒）を数こなす = 高得点は逃すが手数で勝つ

相手のゲージが見えているので、**相手が塞がっている間に長い札を取る**のが正着になる。漢字の知識量が、そのまま「どこまで高い札を狙えるか」という戦術の幅に変換される。握りはミニゲームにしない（クイズの純度が落ちる）。

### 3. 品書きは16枚固定・シャッフルしない

4択にはしない。**壁の品書きから探す行為そのもの**がこの企画の核。

- 一席の間、16枚の配置は**一切変わらない**
- 同じ場所に居続けるから、遊ぶうちに「鰹はあの辺」と手が覚える
- 知識とは別の軸で**上達の実感**が乗る
- 難易度は札の入れ替えではなく、**段位**で構成を変える（後述）

## 操作 / 設定UI ※実装1コミット目はここだけを作る

### 入力方式

| 操作 | タッチ | キーボード |
|---|---|---|
| 札を選ぶ（主操作・これ1つだけ） | 札を直接タップ | 4×4に対応 → `1234` / `QWER` / `ASDF` / `ZXCV` |
| 中断（ポーズ） | 画面下帯の左「⏸ 中断」 | `Esc` または `P` |
| 音を消す | 画面下帯の右「🔇」 | `M` |

- **仮想パッドは作らない。** 十字キーも移動もないため不要
- 入力は **Pointer Events に統一**し、全ボタン・全札に `setPointerCapture` を入れる（押しっぱなしバグの根因対策）
- `touchstart` + `mousedown` の二重バインドはしない
- 札は最小高 56px を確保する

### ポーズの仕様

- プレイヤーが**自分で止められる**こと（`visibilitychange` の自動停止とは別に必ず実装）
- 中断中は**タイマー・握りゲージ・CPU の全てが止まる**
- 再開は3カウント。復帰直後の不意打ちを防ぐ

### 保存キー（`tg.251.*` 形式・接頭辞必須）

| キー | 内容 |
|---|---|
| `tg.251.mute` | ミュート状態（`"1"` / なし） |
| `tg.251.best` | 自己最高の貫数 |
| `tg.251.rank` | 段位（`ichininmae` / `itamae` / `hanaita`） |

既存の `tg.246.mute` 〜 `tg.250.mute` と同じ命名に揃える。接頭辞なしのキーは GitHub Pages が同一オリジンのため他ゲームと衝突する。

## 画面構成（iPhone縦持ち）

「手前に客・奥に職人」を素直に描くと選択肢が画面上部に来て**親指が届かない**。視点をカウンターの内側へ反転させ、**読む（上）→ 押す（下）の一方向**に揃える。

| # | ゾーン | 高さ | 内容 |
|---|---|---|---|
| 一 | スコア帯 | 上端固定 | 左＝自分の貫数／中央＝残り時間／右＝CPUの貫数。safe-area の切り欠きをここで吸収 |
| 二 | 客席とカタカナ注文 | 27% | カウンター越しの向こう側。吹き出しで**大きく1語**。読ませるのはここだけ |
| 三 | 白木のカウンター（対決ライン） | 約12% | 画面を二分する明るい帯。**左＝あなた／右＝CPU**。握りゲージと予約札を並べる。相手の手が塞がっているかが一目で分かる＝戦術の判断材料 |
| 四 | 品書き（親指圏・主戦場） | 残り全部 | 4×4＝16枚。正解で金、お手つきで赤に光る |
| 五 | 中断・ミュート帯 | 下端固定 | 左「⏸ 中断」／右「🔇」。safe-area bottom |

レイアウト検討の全文とモック: https://claude.ai/code/artifact/91b00c73-2364-40c7-a8e0-98214756a63a

## 演出

| 場面 | 演出 |
|---|---|
| 正解 | 札が金に光る → ネタが職人の手元へ飛ぶ → 握りゲージが伸びる |
| お手つき | 札が赤く光り、職人が固まる（2秒）。注文が**相手側へ滑っていく** |
| 握り上がり | 寿司が下駄に乗る音＋貫数がカウントアップ |

## バランスの想定値（**すべて未実測・実装後に調整する**）

| 項目 | 想定値 | 根拠 |
|---|---|---|
| 一席 | 90秒 | 実測で20〜30貫に収まる想定。要調整 |
| 客の待ち時間 | 4.5秒 | 超えると客は帰り、誰の得点にもならない |
| お手つき硬直 | 2.0秒 | タイタン指定値 |
| CPU の誤答率 | 並5% / 上15% / 特上35% | 段位で変える。**未調整** |
| CPU の反応時間 | 0.6〜1.1秒のばらつき | 一定だと機械的に感じるため |
| 1試合の注文数 | 25〜35件 | 上記から逆算。**未検証** |

## iOS対応（`/ios-game-base` 準拠）

- `user-scalable=no` ＋ `touch-action:manipulation`（body）／`none`（品書き格子）の2段構え
- `gesturestart` 抑止 ＋ 350ms以内の連続タップ抑止（ダブルタップ拡大の四重防止）
- `overscroll-behavior:none`（引っぱり更新の抑止）
- 全ボタン・全札が `pointerdown/up/cancel` ＋ `setPointerCapture`
- `env(safe-area-inset-*)` を上下左右に適用
- WebAudio は初回タッチで解錠。`AC` が取れなくても**ゲームは止めない**（try/catch で `AC=null`）
- `prefers-reduced-motion` で札の明滅を停止
- iOSヘッダーCSSは共通ファイルを参照する（手コピー禁止）
- `aria-label` を中断・ミュート・各札に付ける

## 未検証・未決定

- **バランス値は全て机上**。90秒・4.5秒・CPU誤答率は実測していない
- **iPhone実機**での札16枚のタップ精度（4×4で最小高56pxが本当に取れるか未確認）
- 特上4枚が「知らないと絶対に取れない」壁として機能するか。難しすぎると特上を無視する戦略が最適解になり、設計の芯2が死ぬ
- 段位の解放条件（1回の勝利で昇格は緩すぎる可能性）
- 2人対戦（現状の設計はCPU戦のみ）
