# リファクタリング計画書: 帰り道ヒーロー

## 現状分析

### ファイル構成
- **単一ファイル**: `index.html` (5203行)
  - HTML: 約70行 (1.3%)
  - CSS: 約1120行 (21.5%)
  - JavaScript: 約4013行 (77.2%)

### 主な問題点

1. **モノリシック構造**
   - すべてのコードが1ファイルに集約
   - 保守性・可読性が低い
   - 機能追加・修正が困難

2. **重複コード**
   - ステージごとの描画関数が重複（7ステージ × 複数タイプ）
     - `drawBackgroundStage1-7()` (7関数)
     - `drawPlayerStage1-7()` (7関数)
     - `drawEnemyStage1-7()` (多数の関数)
     - `drawBossStage1-7()` (7関数)
   - ボス行動パターンが重複（`updateBossStage1-7()`）

3. **巨大なクラス**
   - `Enemy` クラス: 約500行
     - ボス行動パターンが7つ
     - 通常敵の行動パターンが多数
   - `Obstacle` クラス: 約250行

4. **グローバル変数過多**
   - 約30個のグローバル変数
   - 状態管理が分散

5. **関数の責務が不明確**
   - `update()` 関数が巨大（約280行）
   - `draw()` 関数が巨大（約170行）

## リファクタリング戦略

### フェーズ1: 安全な分割（推奨開始点）

#### 1.1 外部ファイルへの分離（機能を壊さない）
**目標**: 単一ファイルを複数ファイルに分割し、機能を維持

**分割案**:
```
103-帰り道ヒーロー/
├── index.html          (HTML構造のみ、約100行)
├── css/
│   └── style.css       (全CSS、約1120行)
├── js/
│   ├── config.js       (定数・設定、約100行)
│   ├── gameState.js    (ゲーム状態管理、約150行)
│   ├── player.js       (プレイヤー関連、約200行)
│   ├── enemy.js        (敵クラス、約500行)
│   ├── obstacle.js     (障害物クラス、約250行)
│   ├── projectile.js   (弾関連、約300行)
│   ├── item.js         (アイテム関連、約100行)
│   ├── camera.js       (カメラ関連、約50行)
│   ├── renderer.js     (描画関連、約800行)
│   ├── input.js        (入力処理、約200行)
│   ├── audio.js        (音声管理、約150行)
│   ├── ui.js           (UI更新、約100行)
│   └── main.js         (メインループ、約300行)
└── audio/              (既存)
```

**メリット**:
- 機能を壊さずに分割可能
- 各ファイルの責務が明確
- デバッグが容易

**リスク**: 低（HTMLからJSファイルを読み込むだけ）

### フェーズ2: 構造の改善（中リスク）

#### 2.1 描画関数の統合
**目標**: ステージごとの描画関数を統合

**現状**: 
- `drawBackgroundStage1()` ～ `drawBackgroundStage7()` (7関数)

**改善案**:
```javascript
// renderer.js
const StageRenderer = {
  backgrounds: {
    1: (ctx, camera) => { /* 小学生背景 */ },
    2: (ctx, camera) => { /* 中学生背景 */ },
    // ...
  },
  
  drawBackground(stageNum, ctx, camera) {
    const renderer = this.backgrounds[stageNum];
    if (renderer) renderer(ctx, camera);
  }
};
```

**メリット**: コード量削減、拡張性向上

#### 2.2 Enemyクラスの分割
**目標**: ボス行動パターンを別クラスに分離

**改善案**:
```javascript
// enemy.js
class Enemy { /* 基本敵 */ }
class Boss extends Enemy { /* 基本ボス */ }

// bossBehaviors.js
class BossBehavior {
  static stage1(boss, player, camera) { /* ステージ1行動 */ }
  static stage2(boss, player, camera) { /* ステージ2行動 */ }
  // ...
}
```

## 推奨実装順序

### ステップ1: 準備（30分）
1. 現在のコードをバックアップ
2. Gitブランチを作成（`refactoring-phase1`）
3. 動作確認用のテストケースを記録（手動テスト）

### ステップ2: フェーズ1.1 実行（2-3時間）
1. CSSを `css/style.css` に分離
2. JavaScriptを機能ごとに分割
3. 各ステップで動作確認

**分割の順序**:
1. CSS分離（最も安全）
2. 定数・設定の抽出（`config.js`）
3. 音声管理（`audio.js`）- 独立している
4. 入力処理（`input.js`）- 独立している
5. UI更新（`ui.js`）- 独立している
6. 描画処理（`renderer.js`）- 依存関係が多いので最後

### ステップ3: 動作確認（1時間）
- 全ステージの動作確認
- ボス戦の動作確認
- モバイル操作の確認
- パフォーマンス確認

### ステップ4: フェーズ1.2 実行（1時間）
- マジックナンバーの定数化
- 動作確認

### ステップ5: コミット・マージ
- 動作確認後、メインブランチにマージ

## 注意事項

### 絶対に守るべきこと
1. **1ステップずつ進める**: 一度に複数の変更をしない
2. **各ステップで動作確認**: 機能が壊れていないか確認
3. **Gitコミットを細かく**: 問題が起きたらすぐに戻せるように
4. **既存の動作を維持**: 新機能追加は別途

### 避けるべきこと
1. **一度にすべてを変更**: リスクが高すぎる
2. **動作確認なしの変更**: バグの原因になる
3. **命名規則の変更**: 既存コードとの整合性が崩れる
