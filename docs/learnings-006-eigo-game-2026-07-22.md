## 1. 一番の学び：「ゲーミフィケーションの実装」と「ゲーミフィケーションの成立」は別物

旧実装は Lv・XP・ストリーク・実績8種を**約100行かけて実装済み**だった。
にもかかわらず体験としては死んでいた。理由は1つ、**localStorageが無かった**から。

リロードすれば Lv1・XP0・スコア0 に戻る。つまり100行の進捗システムは
「1プレイの間だけ光るメーター」でしかなかった。実績を解除しても次に開けば消える。

> **教訓**: 継続動機の仕掛け（Lv・実績・ストリーク）を実装したら、
> **同じコミットの中で永続化まで入れる**。永続化の無い進捗システムは機能ゼロで
> コードだけが増える。次回以降、進捗系を書いたら必ずセットで確認する。

これは一発生成品に共通する構造だと思われる。生成AIは「見た目の要素」は漏らさず作るが、
**要素が意味を持つための条件**（保存・再訪・復習）は指示されないと作らない。

## 2. 学習系ゲーム特有の見落とし：不正解時に正解が見えていなかった

旧 `selectAnswer` は「押したボタン」にだけ `correct`/`incorrect` を付けていた。
→ 間違えたとき、**どれが正解だったか画面上で分からない**。
解説テキストには書いてあるが、選択肢UIとの視覚的な紐付けが無い。

クイズゲームは「間違えた瞬間」が最大の学習機会なので、ここが弱いと教材として成立しない。
修正後は正解ボタンを必ず緑、誤答ボタンを赤にする（両方同時に光る）。

> **横展開の候補**（※今回は実施しない・鉄則7）: 他のクイズ系ゲームでも同じ実装に
> なっている可能性が高い。棚卸しの機会があれば `.choice-btn.correct` の付与条件を確認する。

## 3. Web Speech API：`setTimeout` + `cancel()` の組み合わせは自爆する

旧コード:
```js
speak(correct);
setTimeout(() => speak(sentenceWithWord), 1000);
// speak() の中身は cancel() → speak()
```
1秒後の発話が**冒頭で `cancel()` を呼ぶため、まだ喋り終わっていない単語を殺す**。
「単語 → 例文」の順で聞かせたかったはずが、実際は単語が途中で切れていた。

正解は `utterance.onend` でチェーンすること。所要時間を推測して `setTimeout` で
繋ぐ設計は、単語長・読み上げ速度・端末で変わるので必ずズレる。

```js
const speakAt = (i) => {
  const u = new SpeechSynthesisUtterance(queue[i]);
  u.onend = () => speakAt(i + 1);   // 時間ではなく完了イベントで繋ぐ
  u.onerror = () => speakAt(i + 1); // 失敗時も止まらせない
  speech.speak(u);
};
```

## 4. `sort(() => Math.random() - 0.5)` は使わない

偏るシャッフルである上に、旧実装は `allQuizData` を**破壊的に**並べ替えていた
（マスタデータをプレイのたびに書き換えていた）。Fisher-Yates + `slice()` に置換。

## 5. 存在しないファイルを読んでいた

`<script src="quizData.js">` — このファイルはリポジトリに存在しない。
実データは `script.js` 側の `fetch("questions.fixed.json")` で読んでいた。
**毎回404を出しながら、たまたま動いていた。**
→ 完了確認時に「HTMLが参照する全パスの実在チェック」を機械的にやる価値がある。
今回は1行のシェルで検出できた:

```sh
grep -oE '(src|href)="[^"h][^"]*"' index.html | sed 's/.*="//;s/"//' \
  | while read f; do [ -f "$f" ] || echo "404 $f"; done
```

## 6. 加えた設計上の判断：弱点優先の重み付き出題

新規追加した唯一の仕組み。`重み = 1 + ミス数×2 − min(正解数, 2)`（下限0.5）。
間違えた単語が次のプレイで出やすくなる。

**なぜ新モードではなくこれを選んだか**: 「もう一度」を押す理由が
「スコアを上げたい」しか無かったのを、「間違えた単語が返ってくる」に変えるため。
モードを増やすより、既存の1モードに再訪の理由を埋め込む方が、
コード量あたりの効果が大きいと判断した。
