## 1. 「AI感」は感想ではなく、コードの特定行として指摘できる

漠然と「AIっぽい」と言われたとき、雰囲気の話にすると直しようがない。旧 `gunkanjima-survival.html` を読んで、
**実在する6行**に還元した。

| 症状 | 現物 |
|---|---|
| 目標に光の柱 | `beamMat` の加算合成シリンダー |
| 常時ナビ矢印＋距離m | `#arrow` `#dist` `target()` |
| 絵文字HUD | `❤️🍙💧⚡` `🥫 缶詰ゲット 🍙+35` |
| 勝利ジングル | `[523,659,784,1047]` ＝ドミソド |
| 回転・浮遊・30秒で再湧き | `it.m.rotation.y+=dt*2` / `respawnQ` |
| 危険の赤い輪 | 落下瓦礫の `ringMat` |

**次に使う条件**: 「AI感がある」と言われたら、まず該当ファイルを読んで症状を**行単位の一覧**にしてから直す。
一覧を SPEC の冒頭に固定しておくと、実装中に元へ戻らない（今回、演出の禁止7条として SPEC 6節に置いた）。

## 2. リアルにするとは、要素を足すことではなく「理由を与え直す」こと

集める物の**個数は減らしていない**（パーツ5個 → 流木4本＋ライター＋布）。変えたのは理由。

- 光る八面体5個 → **運ぶ理由がある物**（火を焚くための流木・火種・着火材）
- 「近づくと拾える」 → **一度に2本しか持てない**（かさばるから）＝往復が必要になり、往復の最中に台風のピークが来る
- 「60秒耐える」 → **波高が1.5mを割った朝にだけ船が入る**（実際の端島上陸が波高で中止になる事実をそのまま条件にした）

体力バー4本も、減る理由と回復手段を現実の因果に差し替えただけで、印象が変わった。
濡れる → 風が当たる → 体温が落ちる → 屋根の残る棟に入る、という連鎖は、**説明しなくても伝わる**。

**次に使う条件**: 「リアルにして」と言われたら、機能追加ではなく、**既存の各要素に「なぜそれが必要か」を一つずつ当て直す**。

## 3. 考証は「寄せた点」と「変えた点」を両方書かないと嘘になる

端島は南北480m。ゲームでは300mに圧縮した。建物配置も実際の測量図ではない。
これを黙って「実在の軍艦島を再現」と書くと誇張になる。SPEC 2節を **寄せた点の表／変えた点の箇条書き**の二段に分けた。

副産物として、圧縮の判断が後から検証できるようになった（なぜ300mか＝全長を走って約70秒）。

## 4. 座標の約束ごとを決めずに方位を出すと、必ず食い違う

コンパスと地図を実装したあと、スクリーンショットで見て初めて気づいた:
**`yaw=0` を「北」にしていたため、島の長辺が東西になり、「南西のドルフィン桟橋」が北にあった。**

- 原因: 3D側は「`-z` が前」という three.js の都合で座標を決め、方位表示はその生の角度をそのまま使った
- 直し: `+x=北 / +z=東` を先に決め、コンパスは `yaw` から −90° 補正。SPEC 8節に約束ごとを明記

**次に使う条件**: 方位・地図・「北へ向かえ」のような台詞を出す作品では、**実装前に「どの軸が北か」を SPEC に書く**。
3Dの前方向（-z）と物語上の北を、暗黙に同一視しない。

## 5. スクリーンショットを撮るまで、レイアウト崩れと黒つぶれは見つからない

harness は **PASS したのに**、実際の画面は次の2点で成立していなかった。

1. **夜が黒つぶれ** — `hemi.intensity=.10+light*.62` では夜の地面がほぼ真っ黒。`.30+light*.52` ＋ 平行光の下限 `.10` で、
   月明かり相当の「輪郭は見えるが細部は見えない」状態になった
2. **HUDが操作系と重なっていた** — 状態文・所持品・体力バーが仮想スティックの上に乗っていた。
   390×844 では左右スティック（各132px）＋中央ボタンで下段が埋まる。**下段は操作系だけにして、状態文は上段へ逃がした**

harness の判定項目（起動・描画ループ・タップ・エラー・容量）に**「画面として成立しているか」は入っていない**。
入れようがないので、人間かAIが実際に絵を見るしかない。

**次に使う条件**: harness PASS を完了条件にしない。**最低でも「起動直後」「昼」「メニュー」の3枚を撮って目で見る**。

## 6. 盲目のキー操作では終盤を検証できない。debugフックは「複製」に入れる

7分後に船が来る設計を、自動テストで頭から遊んで確かめるのは非現実的だった。
かといって出荷物にデバッグ用の抜け道を残すのは避けたい。

やったこと: `index.html` の複製にだけ `window.__dbg`（座標・時刻・状態の読み書き）を注入し、複製に対して検証を回した。

- 屋内退避で体温が戻るか（屋内 +1.05/秒・屋外 −1.03/秒）
- 壁をすり抜けないか
- 地獄段で岩山に上れるか（x=76→58 で y=1.62→10.61）
- t=388 から流して、船影 → 点火 → 「生還」画面まで

**出荷する index.html には debug フックを入れていない。**

**次に使う条件**: 終盤・長時間経過・特定地点でしか起きない事象は、**複製にフックを入れて検証**する。
本体に `?debug=1` を足すより、複製のほうが消し忘れが起きない。

## 7. iPhone を主戦場にするなら、描画コールは作りながら減らす

初回計測で 30 RAF/秒（合格ライン ちょうど）。原因は瓦礫・草の個別メッシュ約180個と、海の頂点1936個。

- 瓦礫・草を `THREE.InstancedMesh` 2個にまとめた（r128 の core にある。アドオン不要）
- 海を 44×44 → 24×24 セグメント、法線再計算を3フレームに1回 → 6フレームに1回

結果 62 RAF/秒。**見た目は変わっていない。**

**次に使う条件**: 「同じ材質の小物を散らす」コードを書いたら、その場で InstancedMesh にする。
後から直すと座標生成のロジックごと書き換えることになる。

## 8. harness の tap 判定は DOM の先頭要素を叩く

`page.locator('button, [role="button"], canvas').first()` を叩くため、**body の先頭が canvas だと、その上を覆うタイトル幕に阻まれて必ず FAIL する**。

直し: タイトル幕（開始ボタンを含む）を canvas より前に置いた。CSS は全要素 `position:fixed` ＋ z-index 管理なので、
**DOM順を変えても重なり順は変わらない**。

副次効果として、harness が「開始ボタンを押して実際にゲームへ入る」ようになり、
起動直後だけでなく**プレイ中のエラーも拾えるようになった**。

**次に使う条件**: 3D/canvas ゲームでタイトル幕を出すなら、**開始ボタンを DOM の先頭側に置く**。
